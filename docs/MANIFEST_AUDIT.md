# Manifest Audit (audit item 13)

Generated by `discovery.Catalog.Audit()` (`discovery/audit.go`), which every
`go test ./discovery/...` run re-checks and logs via
`TestRealEmbeddedCatalog_AuditReport`. Re-run `go test ./discovery/... -run
TestRealEmbeddedCatalog_AuditReport -v` to regenerate this list against
the current manifests.

## Finding

**28 of 28 catalog entries (100%) are missing a SHA256 checksum.** All 28
do have at least one download URL. No entry is missing both.

(Was 29 of 29 as of the previous audit pass — `winxp-pro-i386` has since
been removed from the catalog entirely; see audit item 2.13 / Phase 4
item 22 in `PROGRESS.md`, unrelated to checksums.)

This is a systemic, severe gap: with no checksum, nothing in the download
pipeline (see `engine/streamer.go` and its `TestStreamDownload_*` tests)
can detect a truncated, corrupted, or substituted (e.g. an HTML error page
served as 200 OK) download for **any** preset OS. It is very likely the
root cause behind user reports of "downloads ending incomplete" going
unnoticed until the provisioning step fails later, deep in the pipeline.

## Why this isn't fixed in this change

A real SHA256 checksum can only come from a trustworthy source: either the
distro's own published checksum file (preferred — most Linux distros
publish one, e.g. `SHA256SUMS`), or computing it from an actual full
download of the image. This session:

- Cannot safely download 28 separate, multi-gigabyte OS images to compute
  checksums directly (bandwidth, time, and this task's own rule against
  downloading full ISOs outside a controlled, scheduled CI job).
- Does not have a mechanism to verify a checksum pasted from an external
  source wasn't itself typo'd or stale without downloading the file anyway.

This is fundamentally a **data curation task**, not a code bug — the fix is
either manually sourcing each official checksum (and wiring in Phase 4/item
20's signature verification where distros publish signed checksum files,
which would make this far more trustworthy than a bare SHA256), or running
the `.github/workflows/download-verify.yml` workflow (below) which
downloads each entry via this tool's own downloader and can be extended to
report/backfill a computed checksum once a human has reviewed it came from
the real, intended source.

## What this change does do

- `discovery/audit.go` + `discovery/audit_test.go`: the detection/reporting
  function and its tests, so this gap is visible (`go test -v`) rather than
  silent, and so any **future** entry added without a checksum is caught
  the same way.
- `.github/workflows/download-verify.yml`: downloads each catalog entry
  with this tool's own downloader, verifies it against its manifest
  checksum (when present), flags entries too large for the runner's free
  disk space as `SKIPPED-SIZE`, and uploads a report — on `workflow_dispatch`
  and monthly, **never on push**, per this task's own safety rules about
  not downloading full ISOs in CI on every change.

## Not done in this change (explicitly out of scope here)

- Backfilling the actual 28 checksum values.
- UI-level visual flagging of broken entries in the TUI catalog browser
  (`ui/model.go`'s `GetEntriesByCategory`-driven selection list). The
  detection function above is ready to be wired in; the UI change itself
  was not made in this session due to time, and because — with literally
  every entry currently flagged — a UI change that hides or hard-blocks
  broken entries would leave the tool with zero selectable OS options,
  which is worse than the status quo until checksums are actually
  backfilled.
